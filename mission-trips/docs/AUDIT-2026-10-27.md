# Audit: Mission Trips → Sent (2026-10-27)

## 1. Architecture (as found)

One Next.js 16 app (server-rendered pages + server actions) on PostgreSQL via Prisma 7; Stripe Checkout/Connect for payments; local-disk private file storage; email via an outbox table (Resend in production). Multi-church from day one: every church record carries `orgId`, child records use composite foreign keys so the database rejects cross-church links, and all permissions live in one tested module. Money is integer cents; an append-only ledger (enforced by a database trigger) is the source of every financial total.

## 2. Features and actual status (before this session)

Working and tested: accounts/sessions/password reset; church signup with platform approval; invitations; trips, applications, approvals, leaders, itinerary, documents; participant pages and team fund; Stripe checkout and signed, idempotent webhooks (payments, fees, refunds, disputes, reconciliation); check/cash gifts; pledges kept separate; receipts; requirements (uploads, waivers, forms, tasks) with review and readiness; announcements and donor updates with approval; notifications and reminders; expenses, budgets, ledger, published donor reports; activity log; encrypted medical data; Apple-style responsive UI with dark mode. 75 integration + 12 browser tests.

Not verified: real Stripe (test-mode) flow and Connect onboarding; real email delivery.

## 3. Biggest gaps vs. the Sent vision

- **Financial controls:** leaders' expenses went straight into the ledger; leaders could void paid expenses. *(Fixed this session.)*
- **Proactive readiness:** only counts of applications/reviews; no fundraising-pace, budget-overrun or shortfall detection. *(Built this session.)*
- **Donor transparency:** only manually published snapshots; no live view; reports written from scratch. *(Built this session.)*
- **Integrations:** none; no export for bookkeepers. *(CSV exports and integration plumbing built; live integrations pending.)*
- **Brand:** "Mission Trips". *(Renamed to Sent.)*
- Still missing: Planning Center sync, background checks, SMS, trip cloning, guardian consent for minors, multi-campus hierarchy, billing.

## 4. Security and financial design issues

| Issue | Severity | Status |
| --- | --- | --- |
| Leader-entered expenses counted without approval; leaders could void paid expenses | High (financial control) | **Fixed**: approval required; admin-only payment and voiding of approved expenses; races guarded; audited |
| Ops scripts (`make-admin`, `jobs:run`) didn't load `.env` | Medium (operability) | **Fixed** |
| Stripe flow never run against real Stripe | High before real money | Open: P0 |
| Forbidden pages return HTTP 200 with the not-found page (content hidden) | Low | Open |
| In-memory rate limiting | Medium at scale | Open (single instance for pilot) |
| Local-disk file storage | Medium | Open (persistent disk + backups, or S3 driver) |
| No guardian consent for minors; participant names in public page titles/URLs | High if minors participate | Open: decision needed |
| No 2FA for admins | Medium | Open |
| No error monitoring/automated backups configured | Medium | Open (deployment) |

## 5. Five highest-priority improvements (this session)

1. Two-person control on spending (expense approval).
2. Explainable "Needs attention" engine + reviewed reminders.
3. Donor transparency: opt-in live summary + report drafts from records.
4. Integration layer + bookkeeper CSV exports.
5. Rebrand to Sent; competitive research and validation plan.

## 6. Smallest credible pilot

One church, one trip of 8–15 adults, 8–12 weeks before departure through the final report, with Stripe test mode then live, the church's own waiver/receipt wording, CSV export to its bookkeeper, and weekly measures of staff time, completion rates, and willingness to pay. Details in VALIDATION.md.
